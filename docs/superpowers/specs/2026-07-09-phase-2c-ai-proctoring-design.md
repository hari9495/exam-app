# Phase 2c — AI Proctoring (Signal-Based Risk Analysis) Design Spec

**Status:** Approved, ready for implementation planning.
**Date:** 2026-07-09
**Depends on:** Phase 0 (Foundation), Phase 1a-1d (Core Exam MVP), Phase 2a (Session Enforcement & Anti-Cheat Event Ingestion), Phase 2b (Live Monitoring) — all merged to `main`. Builds directly on Phase 2a's `ProctoringEvent` table and Phase 2b's `AttemptSettlementService.finalize()` single-source-of-truth pattern.

---

## 1. Context and Scope

This is the third and final sub-phase of Phase 2 ("Anti-Cheat & Live Monitoring") from the product roadmap:

2a. Session Enforcement & Anti-Cheat Event Ingestion — done
2b. Live Monitoring (Realtime Monitoring Service) — done
2c. **AI Proctoring** (this spec)

The original roadmap sketch for 2c described a third-party vendor integration for webcam-based proctoring (face presence/match, multiple-face detection, gaze/attention flagging, audio anomaly detection, screen recording). That scope requires a real candidate-facing exam-taking UI — which does not exist yet; every phase through 2b has been backend API plus e2e tests only, and the frontend (`apps/web`) is still a login/dashboard skeleton from Phase 0's verification pass. Building webcam capture into a UI that doesn't exist is a much larger, separate undertaking and is deliberately deferred (see Section 5).

**Goal of this sub-phase:** apply real AI reasoning to the proctoring signals already being collected. Every settled attempt gets a `riskLevel` (`low`/`medium`/`high`) and a short human-readable `summary`, generated by Claude from that attempt's `ProctoringEvent` timeline, surfaced next to its grading result. Instead of a recruiter reading a raw list of `tab_switch`/`copy_paste`/`dev_tools_detected` rows, they get a one-line assessment of what actually happened.

### In scope

- A new `ProctoringAnalysis` record per attempt, computed automatically the moment an attempt settles (submitted/auto_submitted/force_submitted), alongside grading
- A real LLM call (Anthropic Claude API) that reasons over an attempt's event timeline and returns a structured risk level plus summary — not a hand-tuned scoring formula
- A deterministic `skipped_clean` short-circuit for attempts with zero proctoring events — no LLM call, no cost, for the common case
- Resilient failure handling: an API error, timeout, or malformed response is stored as a distinct `failed` status, never a fake score, and never blocks or delays the attempt's own settlement
- A staff-facing on-demand retry (`POST /attempts/:id/reanalyze`) — the only way a `failed` analysis gets a second chance in this phase
- Exposure via the existing `GET /exams/:id/results` response only

### Explicitly out of scope (deferred)

- **Webcam/computer-vision proctoring** (face/gaze/audio/screen) — the original roadmap scope for 2c, deferred until real candidate-facing exam UI exists to capture media from.
- **Live-push of the risk assessment through Phase 2b's `MonitoringGateway`.** This phase stays decoupled from the WebSocket surface entirely — the assessment is a post-hoc artifact viewed alongside grading, not a live monitoring signal.
- **Per-organization prompt or model configuration.** The model and prompt are hardcoded, matching this project's existing pattern of hardcoding thresholds (e.g. the 30-second online window) rather than adding configuration surface nobody asked for.
- **Backfilling analysis for attempts that settled before this phase shipped.** Only attempts settling after this phase deploys get analyzed.
- **Automatic retry/backoff on failure.** A failed analysis stays failed until a human explicitly requests `reanalyze` — no scheduled retry job.

## 2. Data Model

**One new table**, following the exact no-RLS-of-its-own precedent Phase 2a/2b established for `ProctoringEvent`/`CandidateMessage` (reached only through `Attempt` → `Invitation` → `Exam`):

```prisma
model ProctoringAnalysis {
  id         String    @id @default(uuid()) @db.UniqueIdentifier
  attemptId  String    @unique @map("attempt_id") @db.UniqueIdentifier
  status     String    // 'completed' | 'failed' | 'skipped_clean'
  riskLevel  String?   @map("risk_level") // 'low' | 'medium' | 'high' — null only when status='failed'
  summary    String?   @db.NVarChar(Max) // null only when status='failed'
  analyzedAt DateTime  @default(now()) @map("analyzed_at")
  attempt    Attempt   @relation(fields: [attemptId], references: [id], onDelete: Cascade)

  @@map("proctoring_analyses")
}
```

`attemptId` is `@unique` — one analysis per attempt, overwritten (not appended) on retry via `reanalyze`, so there is always exactly one current assessment per attempt, never a history of prior attempts' analyses to reconcile. `status='skipped_clean'` implies `riskLevel='low'` deterministically, without a real LLM call — a `ProctoringAnalysis` row is still created so "we checked and found nothing" is recorded distinctly from "not yet analyzed" (no row) or "we tried and failed" (`status='failed'`, `riskLevel: null`).

Kept as a table separate from `Result`, not new columns on it: this is a satellite of `Attempt`, not of grading, matching how `ProctoringEvent` and `CandidateMessage` already stand apart from `Result`/`Answer`. It also keeps `AttemptSettlementService`'s core grading responsibility untangled from an unrelated AI-analysis concern that can fail and retry independently.

## 3. Module Architecture & Trigger Flow

**New leaf module `ProctoringAnalysisModule`** — imports nothing from `GradingModule`, `AttemptModule`, `CandidateAuthModule`, or `MonitoringModule`, mirroring the leaf-module discipline Phase 2b established for `MonitoringModule`. Two isolated pieces:

- **`ClaudeProctoringClient`** — a pure wrapper around `@anthropic-ai/sdk`. Takes an attempt's event timeline (event types, severities, and timestamps expressed as elapsed seconds since `startedAt` — never raw wall-clock dates, and never candidate name/email/exam content), returns `{ riskLevel, summary }`, or throws. No DB access, no dependency on any other service in this project — trivially fakeable in tests, exactly like `EmailService`'s isolation from the rest of the candidate/invitation flow. `ProctoringEvent.metadataJson` (free-form, not controlled for PII-safety) is explicitly excluded from what's sent — only `eventType`, `severity`, and elapsed-seconds-since-start ever leave the process.
- **`AttemptAnalysisService`** — the DB-aware orchestrator, exposing one method: `analyze(attemptId: string): Promise<void>`. It fetches the attempt's `ProctoringEvent` rows via its own `TenantPrismaService.forTenant` call, short-circuits to `status: 'skipped_clean'` if there are none, otherwise calls `ClaudeProctoringClient` and persists the result (`upsert` on `attemptId`, so a `reanalyze` call cleanly replaces the prior row). Any failure anywhere in this path — API error, timeout, malformed tool response — is caught internally and persisted as `status: 'failed'`; **`analyze()` never throws**, so every caller can safely fire-and-forget it.

**Trigger — single source of truth, mirroring Phase 2b's emit pattern exactly:** `AttemptSettlementService.finalize()` gains one line immediately after its existing `attempt:status` emit:

```typescript
void this.attemptAnalysis.analyze(finalized.id).catch((error) => this.logger.error('Proctoring analysis failed to start', error));
```

This is deliberately **not** awaited inside `finalize()`'s transaction — the LLM call is a slow external network round-trip, and holding a DB transaction open for its duration (potentially seconds) would be a real correctness/performance hazard, unlike Phase 2b's WebSocket emit, which is synchronous and non-blocking by nature. Because `analyze()` never throws (all failure paths resolve into a stored `failed` row), the `.catch()` here is a pure defense-in-depth backstop, not a load-bearing part of the control flow. `finalize()` is the one place all three settlement paths (candidate submit, lazy auto-submit, staff force-submit) already funnel through — exactly why Phase 2b's whole-branch review centralized the `attempt:status` emit there after finding it duplicated across two call sites. The same reasoning applies here: one trigger site, no per-call-site duplication or omission risk.

`GradingModule` imports `ProctoringAnalysisModule` (one more edge into the existing leaf-module graph, alongside its existing `MonitoringModule` import).

**On-demand retry:**

```
POST /api/v1/attempts/:id/reanalyze     staff (exam:manage) -> re-invokes AttemptAnalysisService.analyze()
                                         regardless of current status; the only way a `failed` row
                                         (or a stale `completed` one) gets replaced
```

Added to the existing `AttemptsController`, alongside `force-submit`/`message`/`proctoring-events`, same guard/permission pattern.

**LLM call contract:** the request forces structured output via Anthropic's tool-use — a single `report_risk_assessment` tool with an enum `riskLevel` field and a string `summary` field, with `tool_choice` forcing that specific tool. A response that doesn't produce a valid tool call is treated as a failure, never parsed leniently or guessed at.

**Exposure:** `ExamsService.getResults` gains a `proctoringAnalysis: { status, riskLevel, summary } | null` field per candidate row (`null` only if the attempt hasn't settled yet, or settled before this phase shipped and was never backfilled) — no new endpoint, no change to `GET /exams/:id/results`'s existing shape beyond this additive field.

## 4. Testing Approach

- **Unit tests:** `AttemptAnalysisService.analyze()` — the zero-events short-circuit produces `skipped_clean` with no call to `ClaudeProctoringClient`; a successful client response persists `completed` with the returned `riskLevel`/`summary`; a thrown error from the client (and a malformed/empty response) both persist `status: 'failed'` with null `riskLevel`/`summary`, and `analyze()` itself resolves rather than rejecting in every one of these paths; a second `analyze()` call for the same attempt replaces (not duplicates) the existing row. `AttemptSettlementService.finalize()` — the analysis trigger fires exactly once per finalize call, is not awaited (finalize's own promise resolves without waiting on it), and a rejection from the triggered call is caught and logged, never propagated.
- **Reanalyze endpoint tests:** `exam:manage` is required (existing `PermissionsGuard` pattern); a request for an attempt outside the caller's organization 404s, matching every sibling route on `AttemptsController`.
- **End-to-end flow** (new test file, following the `live-monitoring.e2e-spec.ts` precedent of overriding an external-service provider with a fake — `ClaudeProctoringClient` is overridden with a fake returning a canned `{ riskLevel, summary }`, since unlike Ethereal for email there is no free real sandbox for Claude, and automated tests must never make a real, billed API call): a candidate with proctoring events submits an attempt, `GET /exams/:id/results` shows `status: 'completed'` with the fake's risk level/summary; a candidate with zero proctoring events submits, results show `status: 'skipped_clean'`, `riskLevel: 'low'`, and the fake client is confirmed never called; the fake client is made to throw for one attempt, results show `status: 'failed'`, then `POST /attempts/:id/reanalyze` (with the fake now succeeding) replaces it with `completed`.
