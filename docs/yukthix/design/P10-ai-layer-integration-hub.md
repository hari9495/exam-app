**Agents and copilots (T1, wave 5).** Employee and manager **copilots** in the app, **Slack, Teams and WhatsApp** answer questions and **prepare actions** (apply leave, raise a claim, draft a goal, start a transfer request). The **action contract**: an agent prepares an action only as a normal P03 request or draft for the signed-in person, the **person confirms** it, and every action is audited with the **agent scope**; no agent approves, pays, files a return or changes pay by itself (YX-AI-13). Use is included up to a fair-use allowance; beyond it, **AI credits** (D18; YX-AI-14).

### A3. Guardrails (apply to every AI call)
1. **Human in the loop:** AI suggests; it may give **advisory scores** (ATS candidate-fit score, AI-interview rubric scores) but never makes or executes a decision (approve, reject, pay). A human always decides (P03).
2. **Data minimisation by sensitivity class** (P02): external LLMs never receive Special data (Aadhaar, health, biometrics, POSH, disciplinary). Confidential values (salary, bank, PAN numbers) are masked or excluded unless the feature is explicitly approved (Q2).
3. **Region:** AI calls use providers or endpoints consistent with the tenant's region (P02 Q7); sub-processors are listed.
4. **No training on customer data:** only providers whose terms exclude training on API data; the setting is verified per provider.
5. **Prompt-injection defence:** uploaded documents are treated as data, not instructions; tool calls are restricted to read-only governed APIs (P09 planner).
6. **Per-feature opt-in** at tenant level, **metering** in AI credits (existing), and **audit** of each call (feature, user, data classes sent, tokens), without storing prompt content containing Confidential data.
7. **Explainability:** AI outputs show sources (documents cited, metric definitions) where applicable.

### A4. AI governance (B13)
Owner: a named **AI product lead** (maker) with a second reviewer (checker), as the P07 compliance owner model. Platform-level, so it applies to every tenant; tenants see the results, they don't configure them.

**Model & prompt registry.** Every AI feature (`feature_key`) has a registry entry per version: provider, model id and version, hosting **region**, prompt template version (hash), tools allowed, data classes it may receive (A3.2), eval set version and last result, status (draft / approved / live / retired). A call (`ai_calls`) records the registry version it used, so any output can be traced and reproduced. BYO-key tenants (Q1) map to the same entries with their model recorded.

**Evaluation sets & acceptance thresholds** (starter targets set by the AI product lead; stricter per feature allowed):

| Feature | Eval set | Acceptance threshold (starter) |
|---|---|---|
| Receipt / document OCR | Labelled receipts, PAN, certificates (Indian formats, poor photos, regional scripts) | Field exact-match ≥ 95 % on amount / date / GSTIN; ID numbers ≥ 99 % or routed to human check |
| AI interview rubric scoring (M10 Q4) | Transcripts double-scored by trained humans | Agreement with humans ≥ human-to-human agreement (e.g. weighted kappa ≥ 0.7); no rubric criterion below 0.6 |
| Helpdesk RAG answers (Q8) | Question sets over sample policy corpora, incl. unanswerable questions | Answer supported by a cited passage ≥ 95 %; confidently wrong ≤ 2 %; unanswerable → "not sure / open case" ≥ 90 % |
| LLM-likeness / AI-assistance signals (T04) | Known-human and known-AI answer sets per language and question type | False-positive rate on known-human answers ≤ 1 % at the flagging threshold (a signal, never a verdict, T05) |
| Attrition-risk scoring (B16) | Historical outcomes, time-split | Calibration error ≤ 5 points per risk band; shown as bands, never a single person's decision input alone |
| Drafting / summaries | Rubric review of samples | No invented facts in ≥ 98 % of sampled outputs |

**Regression on change.** A new model, provider, region or prompt version goes live only after its feature's eval set passes the thresholds and shows no significant drop against the current version; results are stored with the registry entry. Provider-forced model retirements follow the same gate before cut-over.

**Drift monitoring.** Weekly, per feature: acceptance / edit / dismiss rates of suggestions, confidence distributions, "not sure" and escalation rates, OCR correction rates, flag rates by segment; an alert fires when a metric moves beyond its control band, and a sampled re-evaluation is run.

**Bias testing beyond face.** Face match is covered by T05 Q8; in addition, **AI interview scores** and **candidate-fit scores** are tested across groups on the eval sets and on live outcomes where lawful (gender, age band, language / region of schooling, disability accommodations used): adverse-impact ratio (4/5ths) and score-gap tests, plus transcript-error rates by accent / language. A failing group gap blocks release or disables the feature until fixed; results are summarised for tenants (feeds A13 fairness analytics).

**Red-team & prompt-injection regime.** Before each feature launch and quarterly: jailbreak and data-exfiltration tests, **indirect prompt injection** planted in policy documents (helpdesk RAG), résumés and cover letters (candidate fit), receipts and uploaded files, and chat inputs (WhatsApp / Slack / Teams assistant); canary instructions must never be followed; tool calls stay read-only (YX-AI-05). Findings are tracked like vulnerabilities (P12).

**AI incident process.** An AI incident = harmful, biased, leaked or badly wrong output at scale, or a provider change that breaks a threshold. Severity levels; per-feature **kill switch** (platform-wide or per tenant) that falls back to the non-AI path; affected tenants told; post-mortem; linked to the P12 incident register (YX-SECOPS-07) whenever personal data is involved.

**EU AI Act (when selling in the EU; corrected 28 Sep 2026, C4).**
- **Dates:** prohibited practices, including **emotion recognition in the workplace**, and the **AI literacy duty (Art. 4)** apply since **2 Feb 2025**. The **Digital Omnibus** (agreed / approved June 2026) postpones the **Annex III high-risk obligations for employment to 2 Dec 2027**.
- **Scope, Annex III(4):** AI used for **recruitment or selection**, **and** AI used for decisions on **promotion and termination**, **task allocation based on individual behaviour or personal traits**, and **monitoring and evaluating the performance and behaviour** of workers. Employee-side features are in scope, not only hiring.
- **YukthiX as provider** of a high-risk feature completes, before it is enabled for an EU-established tenant or EU candidates / workers: risk-management system, data governance for eval / training data, technical documentation, automatic logging (`ai_calls`), instructions for use to the tenant as **deployer**, human oversight (A3.1 already), accuracy / robustness / cybersecurity evidence (eval results above), quality-management system, conformity assessment, EU database registration and post-market monitoring with serious-incident reporting. Target: complete before 2 Dec 2027.
- **Tenant as deployer:** uses the feature per the instructions for use, assigns trained people to human oversight, keeps the logs, and **informs workers' representatives and affected workers before putting high-risk AI into service at the workplace (Art. 26(7))**: YukthiX supplies the notice template ([APX-G](APX-G-legal-artefacts.md) **G-36**) and blocks enabling until the tenant records that it was given (YX-AI-12). Tenant users get the **AI literacy guidance** (APX-G **G-37**, Art. 4) before first use of any AI feature.
- **Emotion recognition** from face or voice in hiring or at work is never built (prohibited practice).
- **"Off for EU tenants" covers all high-risk employment AI** (every "yes" or "depends" row below), not only hiring, until conformity is complete; the other features keep their normal opt-in.

## Part B · Integration hub

### B1. What exists today (exam app)
- **Connected apps:** `OrgIntegration` + `IntegrationDelivery` (outbound events to webhooks / Slack / Teams / Zapier, with retries and a delivery log, URL allow-list). `IntegrationDelivery` failures feed the admin **Jobs & errors** page (APX-D PLT-38, YX-INT-10; G6).
- **Calendar sync:** Google / Microsoft OAuth, free/busy, meeting links.
- **Job boards, Easy Apply, HRIS export, public read-only API + signed webhooks, per-org API key, usage metering.**
- **Encrypted org secrets** (AES-256-GCM).

**Keep** all of this. HR adds **inbound** connectors and file-based exchanges, using the same framework.

### B2. Connector framework
- **Connection:** per tenant (or per legal entity): type, credentials (encrypted), scope, status, health (last sync, errors), owner.
- **Sync jobs** (BullMQ) with idempotency keys, retries with backoff, dead-letter, and per-run logs visible to admins.
- **File exchanges** (bank files, accounting exports) are generated as documents (P05), audited on download (P08), and optionally delivered by SFTP where banks support it.
- **Inbound webhooks** (BGV results, payout status, device pushes) are verified by signature/secret, tenant-mapped and rate-limited.
- **Failures notify** the connection owner (P04), and a "connection health" card appears on the admin home.

## 6. Rules

| ID | Rule |
|---|---|
| YX-AI-01 | AI never makes or executes decisions (no approving, rejecting or paying); it may give advisory scores (ATS candidate-fit, AI-interview rubric scores); outputs are suggestions a person accepts or edits, and a human always decides. |
| YX-AI-02 | Special-class data is never sent to external LLMs; Confidential values are masked/excluded unless the feature is explicitly approved for them; ID-document extraction uses in-region OCR. |
| YX-AI-03 | AI features are opt-in per tenant, metered in AI credits and audited per call (feature, user, data classes, provider, tokens). |
| YX-AI-04 | Providers must contractually exclude training on customer data and be consistent with the tenant's region; they are listed as sub-processors. |
| YX-AI-05 | Uploaded documents are treated as untrusted data in prompts; AI tools are limited to read-only governed APIs. |
| YX-AI-06 | Face templates are Special data: explicit consent, stored encrypted in-region, used only for check-in, deleted on exit or consent withdrawal. |
| YX-INT-01 | Every connection has an owner, encrypted credentials, health status and run logs; failures notify the owner. |
| YX-INT-02 | Inbound connectors are idempotent (duplicate punches/results ignored) and signature-verified. |
| YX-INT-03 | Generated exchange files (bank, accounting, statutory) are documents with hashes; downloads and releases are audited; bank file release follows maker ≠ checker. |
| YX-INT-04 | Public API and webhooks apply the same P02 scopes and field classes as the app. |
| YX-AI-07 | **Registry (B13):** every AI call runs a registered, approved feature version (provider, model, region, prompt hash, allowed data classes) and records that version in `ai_calls`; an unregistered model or prompt cannot be called in production. |
| YX-AI-08 | **Eval gate (B13):** a new model, provider, region or prompt version goes live only after its feature's eval set meets the acceptance thresholds and shows no significant regression, reviewed by a second person; drift metrics are monitored weekly per feature with alerts. |
| YX-AI-09 | **Bias & red-team (B13):** AI interview and candidate-fit scores are tested across groups (adverse-impact 4/5ths and score gaps) before release and quarterly; a failing gap blocks release or disables the feature. Red-team and indirect prompt-injection tests (policy documents, résumés, receipts, chat inputs) run before launch and quarterly; canary instructions are never followed. |
| YX-AI-10 | **AI incidents & EU (B13):** every AI feature has a kill switch (platform or tenant) with a non-AI fallback; AI incidents follow severity, tenant notice and post-mortem, linked to P12 when personal data is involved. High-risk employment AI (Annex III(4), every "yes" / "depends" feature in §A4; YX-AI-11) stays off for EU tenants until EU AI Act provider obligations are met; emotion recognition from face or voice is never built. |
| YX-AI-11 | **EU AI Act classification (C4).** Every AI feature's registry entry (YX-AI-07) states whether it is high-risk under Annex III(4) (yes / no / depends, with the condition) and its EU default; a feature can't go live without it. For EU-established tenants and EU candidates / workers, every "yes" or "depends" feature, hiring **and** employee-side (promotion / termination, task allocation on behaviour or traits, performance and behaviour monitoring), is **off** until YukthiX completes the provider obligations (target before **2 Dec 2027**, the Digital Omnibus date) and ships with human oversight, logging, a transparency notice, bias testing and instructions for use. Emotion recognition at work stays never built (prohibited since 2 Feb 2025). |
| YX-AI-12 | **EU deployer notice & AI literacy (C4).** An EU tenant can enable a high-risk employment feature only after a tenant admin records that the notice to **workers' representatives and affected workers** (APX-G G-36; Art. 26(7)) was given, with date and audience, as a `legal_acceptances` row (audited, P08). The **AI literacy guidance** (APX-G G-37; Art. 4, applies since 2 Feb 2025) is shown to tenant admins before they enable any AI feature and to users before their first use. |
| YX-INT-05 | **Chat apps (B9):** Slack / Teams apps are installed by tenant admin consent, act only for SSO / OAuth-linked users and call the public API as that user (P04 YX-NTF-16). |
| YX-INT-06 | **Mailbox sync (C6):** only threads matched to a candidate, ticket or YukthiX-sent message are imported; send-as uses the user's own OAuth grant; unlinking stops sync at once; synced content takes the attached record's P02 class. |
| YX-INT-07 | **eKYC / DigiLocker (C6):** only via a licensed partner, with explicit per-purpose consent recorded (YX-SEC-28); the full Aadhaar number is never stored (masked + partner reference, YX-SEC-08); pulled documents are stored as issuer-verified P05 documents; a non-Aadhaar path always exists. |
| YX-INT-08 | **Earned wage access (B10):** off unless the company enables it; the accessible amount never exceeds earned net pay to date × company cap; recovery is a payroll deduction within the P07 `IN.WAGES` cap (exit: F&F within the cap); the partner receives only employee id, limit and bank-verified status; YukthiX never funds or lends. |
| YX-INT-09 | **Partner connectors — data minimisation and contracts (gap-register tidy-up).** Every B3 partner connector declares, in its connection record, the data classes it sends and whose contract pays the partner. Content providers, job boards and benchmark data run on the **customer's own licence / account** (connector included, D18); psychometric, plagiarism / leak, eKYC, EWA and benchmark partners are **partner add-ons** (P14 YX-BILL-11). Proctoring partners (psychometric, plagiarism / leak) receive only pseudonymous attempt ids and content, never candidate identity; the benchmark partner receives only job-code queries. Special data is never sent to any partner except eKYC under YX-INT-07. |
| YX-INT-10 | **Jobs & errors page (G6).** `IntegrationDelivery` failures (webhooks / Slack / Teams / Zapier), connector sync-job dead letters (B2), import errors (P15), notification delivery failures (P04) and automation failures (P19 YX-RULE-11) all feed **one admin Jobs & errors page** (APX-D PLT-38) in one record shape: kind, source, record, error in plain words, attempts, next retry, owner. Actions are **Retry** (idempotent, YX-INT-02), **Skip with reason** and open the record; every action is audited (P08). Nothing fails silently: a failure without an owner escalates to the System Admin, and the page's open count is a readiness / health signal (APX-E §2.2). |
| YX-INT-11 | **Deepfake partner connector (T10).** Called only for interview video / audio of a company that has enabled the add-on and a candidate who consented (T04 YX-PROC-20); each call sends the minimal clip / frames, records region, bytes sent and the result in `deepfake_checks`, and is covered by YX-INT-09 (data classes, DPA, no retention by the partner, sub-processor listing). A partner outage skips the check with a note for the reviewer; it never blocks or fails the interview. |
| YX-AI-13 | **Agent action contract (T1).** An agent (copilot, chat-app bot or scheduled assistant) runs only as a registered feature (YX-AI-07) with a declared **agent scope** (actions it may prepare, data classes it may read) no wider than the person's own P02 rights. Every write is prepared as a normal P03 request or draft with source `agent:<feature>` and needs the **person's explicit confirmation** (a confirm button or card, never implied by the conversation); `agent_actions` records person, feature and version, scope, channel and confirmation. Agents can **never approve or reject** a request, release a payment or bank file, **file** a statutory return or **change pay**, CTC or components, even when the person holds those rights; those steps need the person on the app's own screen. A step that fails validation stops and reports; it never retries with a different action. |
| YX-AI-14 | **Copilot channels and credits (T1).** Slack / Teams copilots follow YX-INT-05; **WhatsApp** only on a number the employee has linked and verified (P04), with Confidential values masked in chat and a deep link to the app for anything Special or Confidential. Each tenant has a per-user monthly **fair-use allowance** (P14); beyond it, calls draw AI credits, and with no credits left the copilot answers with links into the app, never losing a pending confirmation. |
| YX-AI-15 | **Plan approval for multi-step agent jobs (P22).** For a "do this for me" request the agent first shows a **plan** (records, changes, screens / APIs, irreversible steps flagged); nothing runs until the person approves the plan. Execution uses only public APIs with the **person's own permissions**, stays inside the approved plan, shows progress, and ends with a summary and undo where reversible. Money (payroll release, payouts, bank files), statutory filing, approving or rejecting others' requests, candidate rejection, dismissal / termination and pay changes each need a **separate explicit confirmation** on the app's own screen and are never run autonomously (YX-AI-13). Plans are stored in `agent_plans` / `agent_plan_steps` and every action in `agent_actions`. Plans that affect employment decisions follow the §A4 classification (a human decides). Use beyond fair use draws AI credits (YX-AI-14). |
| YX-INT-12 | **Global payroll / EOR connectors (T17).** For a country without a YukthiX pack, a company may connect a global payroll or EOR provider: YukthiX **pushes** HR data for workers in that country (joiners, leavers, changes, pay inputs, leave and attendance summaries) and **pulls** results (payslips as P05 documents, gross-to-net totals, employer cost, journals into the accounting export). YukthiX never computes that country's statutory pay; the provider is a listed sub-processor with a data-processing agreement, receives only the fields it needs (YX-INT-09), and pulled results are read-only and period-locked (P08). |

- C6: an eKYC via the partner stores Aadhaar as `XXXX XXXX 1234` with the consent row; no field holds the full number (YX-INT-07).

- T1: in Teams, an employee asks the copilot to apply 2 days' leave; a card shows the prepared request and nothing is submitted until she taps Confirm; a manager asking the copilot to approve a pending request is sent to the app, and `agent_actions` has no approval rows (YX-AI-13).

- T17: for employees in Germany (no pack), a joiner pushed to the EOR provider comes back with a payslip PDF and a cost journal in the accounting export; no German tax calculation runs in YukthiX (YX-INT-12).
